# Задача по проекту dkp-guild-site

«Сделать задачу» = полный цикл до закрытого issue (поручение владельца,
зафиксировано в docs/agent-memory/workflow.md). Не останавливайся на
«код готов» — доведи до слитого PR и закрытой задачи.

### Продолжение работы и реальные препятствия

- Проверяй актуальный статус каждой зависимости и её результат, а не только
  формулировку «заблокировано» в описании issue. Если зависимость выполнена,
  используй её контракт и продолжай задачу.
- Ограничение данных или неоднозначность сначала сопоставь с планом, issue,
  реализованными контрактами и доступными проверками. Если предусмотрен способ
  обработки или допустим обычный технический выбор, реализуй его и продолжай;
  не объявляй задачу заблокированной из-за сложности или неполного исследования.
  Не придумывай игровые правила и не скрывай неопределённость данных.
- Частичный код, успешный отдельный тест или открытый PR — промежуточный этап,
  а не причина завершить работу. Переходи к оставшейся реализации, проверкам,
  CI и закрытию issue, пока это разрешено и возможно.
- Если действительно требуется решение владельца, недоступен обязательный
  ресурс или дальнейшее действие не разрешено, сначала выполни независимую
  разрешённую работу. Затем сообщи конкретное препятствие, что проверено и
  какой ответ или изменение внешнего состояния необходимы. Не называй задачу
  завершённой до выполнения её приёмки и полного цикла.

## Чек-лист

1. [ ] Взять issue (ассайн, зависимости, занятость)
2. [ ] Обновить знания по проекту (PLAN.md + agent-memory)
3. [ ] Ветка + реализация с тестами
4. [ ] Проверки локально
5. [ ] PR + зелёный CI + squash-merge
6. [ ] Закрыть issue с комментом, убрать ветки, погасить серверы, обновить память
7. [ ] Ретроспектива цикла (§7)

## 1. Взять issue

- Открытые issue: GitHub API (`gh`-CLI нет):
  `curl -s -H "Authorization: token $TOKEN" .../issues?state=open` с токеном
  из `git credential fill` (см. «GitHub через API» ниже).
- Выбор: milestone = этап плана; порядок внутри этапа — по списку состава
  в issue приёмки этапа и зависимостям («Зависит от #N»). Заблокированную
  задачу не брать; задачи с «согласовать с владельцем» (типа #101) — не брать
  без его решений.
- Занятость: если у issue есть assignee не ты — не брать, спросить владельца.
- Ассайн на себя: `POST /issues/N/assignees {"assignees":["<git user>"]}`.

## 2. Знания по проекту (обязательно перед кодом)

- `docs/PLAN.md` — единственный источник требований и игровых правил.
  Противоречия решает план; менять его без явной просьбы владельца нельзя.
- `docs/agent-memory/architecture.md` — карта модулей и обязательные
  ограничения (append-only журнал ДКП, настройки не константами, аудит
  ручных действий, приватность на сервере, UI только русский).
- `docs/agent-memory/workflow.md` — команды, проверки, жизненный цикл,
  делегирование; `known-issues.md` — ловушки окружения.
- Для UI: `docs/ui/` (представление экранов) и `apps/web/DESIGN.md`
  (палитра и примитивы).

## 3. Ветка и реализация

- Ветка `feature/<issue>-<slug>` (или `fix/`, `docs/`) от свежего `main`.
- **Перед каждым коммитом — `git branch --show-current`**: в дереве
  параллельно работает вторая сессия и может переключить его на `main`;
  несмонтированные правки при switch между ветками на одном коммите
  сохраняются.
- Конвенции, проверенные предыдущими задачами:
  - логика ядра — в `packages/shared` (zod-схемы + чистые функции),
    юнит-тесты в том же PR (`packages/shared/src/*.test.ts`);
  - сервисы API — с минимальным интерфейсом БД для юнит-тестов без Prisma
    (образец: `apps/api/src/bids/bids.service.ts`); гонки — сериализуемые
    транзакции через `serializable()` с перечитыванием статуса;
  - каждый новый эндпоинт обязан иметь контракт в
    `apps/api/src/openapi/contracts.ts` (+ схемы входа/ответа) — иначе
    падает `openapi.spec.ts`;
  - ручные действия пишут `AuditLog` с автором и обязательной причиной;
    финансовые записи — идемпотентные ключи `DkpEntry.requestId`;
  - UI — примитивы `apps/web/components/ui`, стили страницам не писать;
    после правок UI — скриншоты desktop+mobile в `docs/screenshots/`.
- **Батч фикстур после смены общих типов** (урок #101): добавил/изменил
  обязательные поля в типы shared (BidRow, AuctionListRow, …) — сразу же
  найди ВСЕ литералы этих типов в `*.spec.ts`/`*.test.ts(x)` (grep по имени
  типа и по характерным полям) и почини их одним заходом. Цикл
  «typecheck → пара ошибок → фикс» по шесть раз дороже одной пакетной правки.
- Код правь только инструментом Edit — inline `node -e`/sed с многострочными
  заменами из Git Bash ломаются и съедают время на отладку.

## 4. Проверки локально

**Гигиена портов — до любых запусков** (поручение владельца 2026-11-16):
прежние сессии периодически оставляют поднятые серверы, и порт оказывается
занят. Перед прогоном тестов с БД и перед подъёмом стенда проверь, что
локально нет запущенных приложений:

```bash
netstat -ano | grep LISTENING | grep -E ':(3000|3001|3005|3090)[[:space:]]'
scripts/dev-screenshot.sh status   # занятость портов стенда и health
```

- Порты `:3005`/`:3090` (скриншотный стенд) и `:3000`/`:3001` (dev) заняты —
  сначала `scripts/dev-screenshot.sh status`: он покажет, кто держит порты
  стенда. Остаток стенда убирает `scripts/dev-screenshot.sh down` — он снимает
  деревья процессов целиком и не трогает стенд другого каталога (вторая
  сессия в другом клоне). Остальное — определи PID владельца (`netstat` выше,
  `Get-Process -Id <pid>`) и сними дерево зависшего процесса прошлых сессий:
  `taskkill //PID <pid> //T //F` — порт API слушает дочерний процесс
  `nest start --watch`, одного слушателя мало. Свои серверы из прошлых
  запусков убивай без спроса.
- Единственное исключение — явно живая вторая сессия владельца (процесс
  свежий, сервер отвечает на health и ты знаешь, что владелец с ним
  работает): её не трогай, предупреди владельца и используй свободные порты
  (стенд потому и на `:3005`/`:3090`).
- **Не маскируй коды ошибок конвейером** (урок #203): `cmd | tail && next`
  возвращает код `tail`, поэтому сбойный `docker compose up -d` выглядит
  успешным, и стенд поднимается наполовину, а процессы утекают в фон.
  Проверяй результат каждого шага (`set -o pipefail` или отдельные вызовы)
  и читай вывод, прежде чем идти дальше.

```bash
pnpm lint && pnpm typecheck && pnpm test && pnpm build
# интеграционные на реальной PostgreSQL (docker compose up -d):
ONBOARDING_TEST_DATABASE_URL=postgresql://dkp:dkp@127.0.0.1:5432/dkp_test?schema=public \
  pnpm -C apps/api exec jest --runInBand --testPathPattern=database.spec.ts
```

- `dkp_test` общая для всех database-спек: убирай свои ряды в `afterAll`
  (FK-безопасный порядок, образец — `auction-manage.database.spec.ts`);
  не оставляй просроченных OPEN-лотов — они ломают чужие тесты свипера.
- Скриншотный стенд — одной командой: `scripts/dev-screenshot.sh up`
  (API `:3005` на тест-БД с `AUTH_TEST_MODE=true` + web `:3090`, прокси
  переключается и откатывается сам; сид test-юзеров и миграции применяются),
  уборка — `scripts/dev-screenshot.sh down`. Вход под игроком:
  `POST /auth/test-login {"username":"test-member"}` + `GET /auth/me`
  (без /me сессия без Member и прав); резервный админ —
  `POST /auth/admin/login` из `apps/api/.env`. Кириллицу в тела — файлом +
  `--data-binary @file`. Тестовые данные создавай через API и отменяй/чищи
  за собой.
- **Проверяй каждый скриншот (глазами/visual) ДО разбора стенда** (урок #101:
  пересъёмка из-за длинного label стоила второго подъёма стенда).

## 5. PR и CI

GitHub через API (см. workflow.md):

```bash
TOKEN=$(printf 'protocol=https\nhost=github.com\n' | git credential fill \
  | grep '^password=' | cut -d= -f2)
```

- Тела с кириллицей — файлом в `$TEMP` + `--data-binary @file`
  (inline-JSON из Git Bash ломается).
- PR: заголовок `тип: суть (#issue)`, тело — что сделано, правила плана,
  тесты, скриншоты относительными путями.
- CI: опрос `GET /repos/.../commits/<sha>/check-runs` финального коммта
  до `completed/success` (обычно 2–4 мин).
- Merge: `PUT /pulls/N/merge`, squash, заголовок `тип: суть (#issue) (#PR)`.

## 6. Финал

- Закрыть issue: `PATCH /issues/N {"state":"closed","state_reason":"completed"}`
  + короткий комментарий: что влито (PR, squash-коммит), статус CI,
  покрытие приёмки.
- **Погаси все свои локальные серверы** (поручение владельца 2026-11-16):
  `scripts/dev-screenshot.sh down` для стенда (выходит с кодом 1, если порт
  держит стенд другого каталога, — его не трогать), остановка любых поднятых
  тобой dev-процессов (node/nest/next). Затем проверь `netstat`, что порты
  `:3005`/`:3090` (и `:3000`/`:3001`, если поднимал) свободны, и добей
  оставшиеся свои процессы `taskkill //PID <pid> //T //F`. Не оставляй серверы
  работать в фоне после цикла — они занимают порты следующих сессий.
- `git switch main && git pull --ff-only`, удалить ветку локально и на
  origin, `git fetch --prune` (на origin держим только `main`).
- Попутные дефекты — отдельные issue, не чинить молча в чужом PR.
- Обновить `docs/agent-memory/*` при изменившихся фактах (карта модулей,
  ловушки) — тем же циклом через маленький docs-PR.

## 7. Ретроспектива цикла

После закрытия задачи — короткая ретроспектива (2–3 минуты, для себя;
не ради отчёта):

- **Что хорошо** — приёмы, которые ускорили цикл и стоит закрепить.
- **Что стоило лишнего времени** — лишние прогоны тестов, перепробованные
  пути, правки не тем инструментом, мусорные артефакты (в т.ч. в корне
  репо), непроверенные предположения об окружении/фреймворке.
- Универсальные уроки фиксируй в личной памяти агента (файлы вида
  `retro-*`/`execution-speed-lessons`), а факты, переживающие задачу
  и полезные другим, — в `docs/agent-memory/*` отдельным docs-PR.
- Новых уроков нет — фиксировать нечего, переходи к следующей задаче;
  не разворачивай церемонию ради формальности.
