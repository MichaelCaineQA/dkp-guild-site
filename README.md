# ДКП-система гильдии (Throne and Liberty)

Сайт для гильдии: расписание ивентов с игровым временем (день/ночь), отметка
посещения чек-ин кодами, ДКП-журнал, открытый аукцион лута, профили игроков
(прайм-тайм, gear score), структура КП/паков и статистика.

**Полный план проекта: [docs/PLAN.md](docs/PLAN.md)** — требования, механики,
зафиксированные решения гильдии (раздел 12), этапы разработки.

## Стек

- Монорепозиторий: pnpm workspaces + Turborepo, TypeScript strict
- Frontend: Next.js (React) — `apps/web`
- Backend: NestJS + Prisma + PostgreSQL — `apps/api`
- Общий код (типы, zod-схемы, логика ДКП и игрового времени) — `packages/shared`
- Realtime (аукцион): Socket.IO + Redis — подключается на этапе 2
- CI: GitHub Actions — lint → typecheck → test → build → audit

## Быстрый старт (локально)

### Вариант A — весь сайт в Docker одной командой

Нужен только запущенный Docker Desktop (Windows/macOS). Собирает образы,
поднимает web + api + PostgreSQL + Redis, применяет миграции и стартовые
данные при запуске:

```bash
pnpm site:up     # web: http://localhost:3000, api: http://localhost:3001/health
pnpm site:down   # остановить (данные БД сохраняются в томе)
pnpm site:logs   # логи api и web
```

**Запуск Docker Desktop из терминала** — если иконка на рабочем столе
не открывает окно (бывает после сбоев/зависших процессов):

```bash
# Windows, Git Bash:
"/c/Program Files/Docker/Docker/Docker Desktop.exe" &
# Windows, PowerShell:
Start-Process 'C:\Program Files\Docker\Docker\Docker Desktop.exe'
# macOS:
open -a Docker
```

Готовность движка (~30–60 сек) проверяется командой `docker info` —
она должна вывести версию сервера, а не ошибку подключения. Если
Docker «залип» (процессы есть, движок не отвечает): завершить все
процессы Docker в диспетчере задач и запустить снова командой выше;
при проблемах WSL помогает `wsl --shutdown`, затем старт Docker.

Секреты (Discord, `SESSION_SECRET`, …) читаются из `apps/api/.env` —
см. раздел «Вход через Discord» ниже. Без файла сайт поднимется с
dev-дефолтами, но вход будет только через настроенный Discord OAuth
(или резервный админ, если задан `ADMIN_PASSWORD`).

**Если порты заняты/заблокированы** (на Windows после перезапуска Docker
WinNAT может резервировать диапазоны — ошибка `ports are not available`
или `EACCES`): задайте свои порты в **корневом** `.env`:

```env
SITE_WEB_PORT=3080
SITE_API_PORT=3081
NEXT_PUBLIC_API_URL=http://localhost:3081   # = SITE_API_PORT
WEB_URL=http://localhost:3080               # = SITE_WEB_PORT
```

Проверить зарезервированные диапазоны:
`netsh interface ipv4 show excludedportrange protocol=tcp` (Windows).
Не забудьте также `DISCORD_CALLBACK_URL` — см. ниже.

### Вариант B — обычная разработка (web/api локально)

Нужны Node.js ≥ 20, pnpm и Docker:

```bash
corepack enable          # если pnpm ещё не установлен
pnpm install
docker compose up -d     # PostgreSQL + Redis
pnpm db:generate         # сгенерировать Prisma-клиент
pnpm db:migrate          # применить миграции (создать таблицы)
pnpm db:seed             # стартовые данные: гильдия, типы ивентов, настройки
pnpm dev                 # web: http://localhost:3000, api: http://localhost:3001/health
```

Переменные окружения — по образцу [.env.example](.env.example) (копируются
в `apps/api/.env`). Для миграций и seed нужен `DATABASE_URL`.

Команды `pnpm db:seed` и `pnpm db:seed:test` сами собирают `@dkp/shared`
и генерируют Prisma-клиент. `pnpm db:migrate` также предварительно собирает
общий пакет, чтобы автоматический seed новой БД мог импортировать его.
Каталог `packages/shared/dist` генерируется локально и не хранится в Git.

## Развёртывание и эксплуатация

### Установщик релизов на VPS (простой путь)

По тегу `v*` workflow Release публикует на GitHub Releases архив
`dkp-guild-site-<версия>.tar.gz` с контрольной суммой; образы api/web
(multi-arch amd64/arm64) уходят в GHCR и фиксируются в манифесте релиза
по digest. Установщик — скрипт `dkp` на Python 3 (только стандартная
библиотека) для Ubuntu 22.04/24.04. Нужны домен, чей DNS указывает на VPS,
свободные порты 80/443 и доступ администратора. Пошаговая инструкция —
[installer/README.md](installer/README.md); приёмка на чистой VM ещё
не проводилась (#75).

Обычно все команды запускаются через sudo (`./dkp help` — краткая справка):

- **`start`** — мастер первичной настройки: домен (проверяется DNS
  и подтверждается вручную), название гильдии, логин и пароль
  администратора, необязательный Discord и параметры резервного
  копирования. Недостающий Docker Engine с Compose устанавливает
  через apt после явного подтверждения. Затем скачивает образы по digest,
  применяет миграции и seed, поднимает `db`, `redis`, `api`, `web` и
  `caddy` (автоматический HTTPS) и ждёт успешного ответа
  `https://<домен>/api/health`.
- **`update [v1.2.3]`** — обновление до свежего или указанного релиза:
  скачивает архив с GitHub Releases, проверяет контрольные суммы
  и состав, создаёт резервную копию, останавливает API, применяет
  миграции и переводит установку на новый релиз. При ошибке миграции API
  остаётся остановленным (`status` подсвечивает проблему) до восстановления
  копии; смена образа сама по себе не откатывает БД.
- **`backup setup | now | list | restore <id>`** — резервные копии единым
  пакетом: дамп БД (`pg_dump`), архив скриншотов, конфигурация и манифест
  релиза. Пакет шифруется `openssl` (AES-256-CBC, PBKDF2) ключом
  восстановления и подписывается HMAC-SHA256; выгрузка по SSH на отдельный
  сервер (атомарно, без частичных файлов) или в локальный каталог, ротация —
  по сроку хранения. Расписание — ежедневный systemd-таймер с нужным
  часовым поясом. `restore` проверяет подпись и состав, поднимает релиз
  той же версии, предварительно создаёт страховочную копию и просит
  подтвердить домен; ключ восстановления нужен и для восстановления —
  храните его вне VPS и хранилища копий.
- **`status` / `logs [сервис]` / `stop` / `restart` / `configure` /
  `leader`** — версия, домен, результат последнего бэкапа, состояние
  контейнеров и health-проверка; логи `api|web|db|redis|caddy`; изменение
  домена, админа или Discord; напоминание назначить Главу через UI —
  установщик его не назначает.

Состояние установки — `/var/lib/dkp-guild` (конфигурация с правами 0600,
каталоги релизов и копий, флаг прерванной миграции). Сервисы работают
в изолированном Compose-проекте `dkp-guild`; одновременные операции
исключены файловой блокировкой, а команды управляют только этим проектом —
TeamSpeak и другие службы сервера не затрагиваются. Автоматическое
обновление рассчитано на публичные release assets; приватные релизы и образы
GHCR требуют отдельной авторизации GitHub/Docker и проверки видимости
пакетов владельцем репозитория.

### Deploy из исходников

Описанный ниже deploy из исходников — существующий способ развёртывания,
полностью управляемый из checkout репозитория. Production-конфигурация
подготовлена в `docker-compose.prod.yml` и `Caddyfile`. На отдельном Linux
VPS установите Docker Engine с Compose и Git; направьте DNS имён сайта и API
на сервер, откройте порты 80 и 443. Не включайте проксирование DNS через
Cloudflare. Подойдут VPS с локацией в ЕС, например Selectel или Timeweb
Cloud, и домен у любого регистратора (например, reg.ru).

1. Разместите checkout проекта в постоянном каталоге сервера и скопируйте
   `.env.production.example` в `.env.production` в этом каталоге; ограничьте
   права файла: `chmod 600 .env.production`.
2. Укажите два домена, учётные данные PostgreSQL и резервного
   администратора. Значение `DATABASE_URL` должно соответствовать PostgreSQL;
   специальные символы пароля в URL кодируются percent-encoding. Создайте
   независимые секреты `SESSION_SECRET` и `CHECKIN_ENC_KEY` (последний —
   64 hex-символа, например `openssl rand -hex 32`). В Discord укажите
   callback `https://<WEB_HOST>/api/auth/discord/callback`. Настройку Discord
   можно отложить: оставьте `DISCORD_CLIENT_ID` и `DISCORD_CLIENT_SECRET`
   пустыми; API запустится, а на экране входа останется доступ
   администратора. После заполнения обоих значений пересоздайте API через
   Compose; пересборка web не нужна.
3. Запустите `sh scripts/deploy-prod.sh`. Скрипт собирает образы,
   останавливает API, делает снимок БД и файлов, применяет миграции и seed,
   запускает сервисы. При ошибке миграции API остаётся остановленным до
   проверки. Caddy получает сертификаты автоматически; проверьте
   `https://<WEB_HOST>/api/health` и сайт.

Браузер обращается к API через `/api` на домене сайта. Caddy убирает этот
префикс перед передачей запроса API; cookie и приватные скриншоты проходят
тем же путём. Образ web по умолчанию собирается с `/api`, без привязки
к домену. Для будущего realtime зарезервирован путь `/api/socket.io/`: Caddy
поддерживает WebSocket через тот же прокси; API использует Socket.IO gateway
для событий аукциона.
Отдельный `API_HOST` сохранён для совместимости существующего deploy
и диагностики. При обновлении добавьте новый callback в Discord Redirects
до переключения; для временного сохранения прежнего задайте
`DISCORD_CALLBACK_URL` явно. `PUBLIC_API_URL` больше не задаёт адрес API
для production web-образа.

### Деплой через GitHub Actions

Workflow `Deploy` запускается после успешного CI пуша в `main`: проверенный
SHA уезжает на стенд через окружение `staging`: Linux runner передаёт
checkout через `git archive` по SSH, затем запускает `scripts/deploy-prod.sh`.
Для ручного запуска (workflow_dispatch) настроите GitHub environments
`staging` и `production`: secrets `DEPLOY_HOST`, `DEPLOY_USER`,
`DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS` (проверенный ключ сервера)
и variable `DEPLOY_PATH` (абсолютный путь к checkout с заранее
настроенным `.env.production`).
Для staging выберите проверенный коммит main и окружение в Actions → Deploy → Run workflow.
Ручной деплой также требует успешного CI именно выбранного SHA. После
развёртывания браузерный smoke сверяет SHA в health и открывает страницу входа.
Для production запускайте workflow из `main`, выберите `production` и заполните
`release_tag` (например `v1.0.0`). Можно также отправить workflow_dispatch
непосредственно с ref тега, без `release_tag`. Тег должен существовать и указывать
на коммит из истории `main`; ветка без тега и тег невлитой ветки отклоняются
до SSH. Создание тега само по себе production не обновляет. Теги `v*` отдельно
запускают workflow Release: Linux runner проверяет сборку, миграции, тесты,
установщик и упаковщик, затем публикует установщик и образы. Release archive
формируется на Linux; перед публикацией smoke check проверяет распаковку,
состав, LF, исполняемость установщика и контрольные суммы.

Обычный релиз: дождаться зелёного CI и автоматического деплоя `main` на stage,
проверить **конкретный SHA** через `/api/health`, поставить на него новый тег,
дождаться Release и вручную запустить Deploy с этим тегом. Опубликованные теги
не передвигать. В GitHub environment production разрешите dispatch из `main`
и тегов, запретив остальные ветки. Деплои двух стендов сериализуются серверным
`flock /run/lock/dkp-deploy.lock`, включая распаковку архива.

**Стенд `stage.suneclipse.ru`** (окружение `staging`, VPS 188.120.225.204):
checkout `/opt/dkp-guild-site` с локальным `.env.production`; каждый пуш
в `main` обновляет его автоматически. DNS-запись должна указывать прямо
на VPS (без проксирования Cloudflare), иначе Caddy не получит сертификат
Let's Encrypt и не будут работать WebSocket-обновления аукциона.

### Production и stage на одном VPS

Production: `suneclipse.ru`, API `api.suneclipse.ru`, каталог
`/opt/dkp-production`, Compose-проект `dkp-production`. Stage сохраняет
`/opt/dkp-guild-site` и проект `dkp-guild-site`. У каждого свой
`.env.production` (0600), БД, Redis, том скриншотов и каталог `backups`.
Данные stage не копируются в production. Discord для production требует
Redirect `https://suneclipse.ru/api/auth/discord/callback`; без OAuth доступен
резервный администратор из production env.

Оба приложения работают с **пустым** `COMPOSE_PROFILES=`. Для одиночного
сервера оставляйте `COMPOSE_PROFILES=standalone`, как в env-примере.
При переходе существующего standalone-стенда добавьте это поле явно.
В env двух стендов задайте уникальные upstream-алиасы:

| Поле                   | Stage            | Production       |
| ---------------------- | ---------------- | ---------------- |
| `COMPOSE_PROJECT_NAME` | `dkp-guild-site` | `dkp-production` |
| `API_UPSTREAM`         | `staging-api`    | `production-api` |
| `WEB_UPSTREAM`         | `staging-web`    | `production-web` |

Порты 80/443 занимает отдельный проект `dkp-edge`. Файлы
`docker-compose.edge.yml` и `Caddyfile.edge` размещаются в `/opt/dkp-edge`;
edge присоединяется к существующим сетям двух приложений. Поднимите оба
стека (`sh scripts/deploy-prod.sh` в каждом каталоге), затем остановите
старый Caddy stage (`docker compose --env-file .env.production
-f docker-compose.prod.yml stop caddy`) и запустите edge:

```bash
cd /opt/dkp-edge
docker compose -f docker-compose.edge.yml up -d --wait
```

Переключение освобождает 80/443 и кратко прерывает HTTPS stage; его БД и тома
сохраняются. Edge обновляется отдельно от деплоев приложения. При правке его
конфигурации сначала выполните `caddy validate`, затем `caddy reload` в
контейнере. Не запускайте standalone Caddy одновременно с edge.
Проверьте `/api/health` и HTTPS обоих сайтов; SHA должен соответствовать
выбранному для каждого стенда коммиту. GitHub variable `DEPLOY_PATH`
production должна быть `/opt/dkp-production`, staging — `/opt/dkp-guild-site`.

### Откат релиза production

Перед миграциями Deploy останавливает API и создаёт снимок базы и скриншотов
(`scripts/deploy-prod.sh`). Имя комплекта — в журнале запуска Deploy, строка
«Резервная копия: …»; комплекты лежат в `/opt/dkp-production/backups`.

- **Схема данных не менялась или прежняя версия с ней совместима.** Запустите
  Deploy вручную: `environment=production`, `release_tag` — прежний тег.
  Workflow пересоберёт образы тега, снова сделает снимок и запустит
  приложение; данные приложения остаются на месте.
- **Новые миграции несовместимы с прежней версией.** Смена образа базу не
  откатывает: сначала восстановите базу и скриншоты из предрелизного комплекта,
  затем запускайте Deploy прежнего тега. Такой откат проверяйте на учении до
  выпуска (контрольное восстановление — ниже).

После отката поле `commit` в `https://suneclipse.ru/api/health` должно совпасть
с SHA тега. Между `v0.4.0` и `v1.0.0` миграций нет: для возврата с `v1.0.0`
достаточно первого пути. Пять миграций между `v1.0.0` и `v1.1.0` только
добавляют таблицы и колонки Discord-очереди, поэтому для возврата с `v1.1.0`
на `v1.0.0` тоже достаточно первого пути.

### Discord-бот уведомлений

Токен бота задаётся отдельно от OAuth-пары `DISCORD_CLIENT_ID` /
`DISCORD_CLIENT_SECRET`. Для production/stage добавьте `DISCORD_BOT_TOKEN`
в соответствующий `.env.production`: используйте разные боты и токены для
stage и production. Installer читает `DKP_DISCORD_BOT_TOKEN`
из своего env-файла и передаёт его API как `DISCORD_BOT_TOKEN`. После изменения
пересоздайте API (`docker compose ... up -d --force-recreate api`). Токен
не коммитьте и не публикуйте в логах. Пустое или отсутствующее значение
отключает подключение бота; для отключения очистите переменную и пересоздайте
API.

В каждом окружении задайте `DISCORD_GUILD_ID` — ID разрешённого Discord-сервера
(для installer — `DKP_DISCORD_GUILD_ID`). Для staging используйте отдельные
тестовый сервер и бота, не добавляйте staging-бота на боевой сервер.
Без обоих значений отправитель отключён. Очередь и настройки привязаны к ID
сервера: записи, перенесённые из другого окружения, не отправляются. Старые
записи без ID сервера автоматически не отправляются; перед ручным исправлением
необходимо проверить адресата и риск дубля.

Создайте приложение и bot в Discord Developer Portal, скопируйте bot token,
затем добавьте бота на сервер гильдии с минимальными правами в целевом канале:
**View Channel** и **Send Messages**. Не выдавайте Administrator. Если бот
не видит канал, проверьте разрешения канала и настроенный для него ID.

Каналы задаёт Глава или Админ в блоке «Discord» на странице настроек: ID
текстовых каналов сервера гильдии для анонсов, напоминаний, заявок об
отсутствии и итогов лотов. Пустое поле отключает уведомления этого типа;
один канал подходит для нескольких типов, включая заявки об отсутствии (в
сообщении — ник, период и событие, без причины). При сохранении сайт
проверяет через Discord принадлежность канала настроенному серверу и право
бота писать в него и записывает изменение в аудит; «Проверить сохранённый
канал» отправляет нейтральное тестовое сообщение.

Напоминания по умолчанию отправляются за 15 минут; Глава или Админ может
изменить интервал на странице настроек (от 1 минуты до 7 дней). Событие,
созданное или перенесённое внутрь окна, попадает в очередь при ближайшем
проходе. При переносе прежнее напоминание отменяется, для новой даты возможно
новое; изменение интервала не повторяет уже отправленное напоминание для того
же времени начала. После перезапуска очередь восстанавливается, но события,
которые уже начались, не рассылаются.

Outbox-модель `DiscordNotification` хранит очередь (поля `status`,
`attempts`, `availableAt`, `lastError`, `sentAt`). При проблемах сначала
проверьте, включён ли отправитель в используемой версии, затем логи API
(`docker compose logs --since=30m api`) и доступность Discord/канала. Для
диагностики записей можно выполнить на сервере:

```sql
SELECT status, count(*) AS count, min("createdAt") AS oldest,
       max("lastError") AS last_error
FROM "DiscordNotification"
GROUP BY status
ORDER BY status;
```

Имена полей в БД — quoted camelCase. Не сбрасывайте статус и не создавайте
копии записей для ручного повтора: если Discord принял сообщение, но ответ
потерялся, повторная отправка может дать дубль. Сверьте канал и время сообщения
перед любым повтором; неоднозначный результат доставки требует учитывать риск
дубликата. Очередь сама по себе не означает, что все типы уведомлений или
пользовательский интерфейс настройки уже доступны, а наличие записи не
подтверждает фактическую доставку.

`PENDING` означает ожидание или отложенный повтор, `SENT` — подтверждённый
ответ Discord, `FAILED` — постоянная ошибка (например, `HTTP_403`: проверить
права бота). Ошибки и сетевые ответы не записываются в журнал целиком.
При 429 общая пауза сохраняется в `DiscordDeliveryGate`; после сбоя сети
отправка повторяется с тем же nonce. Discord устраняет повторы по nonce
лишь в течение ограниченного времени, поэтому доставка не гарантирует
отсутствие дублей после долгого сбоя или потери ответа.

Установите отдельное ежедневное расписание бэкапа production; используйте
общую блокировку `/run/lock/dkp-deploy.lock` для cron обоих стендов, чтобы
копирование не пересекалось с миграциями. Внешнее хранилище, хранение 30 дней
и контрольное восстановление настраиваются по следующему разделу.

### Локальная HTTPS-проверка production-стека

Для локальной HTTPS-проверки используйте отдельный каталог и проект Compose,
отдельные порты и тестовые секреты; в env задайте `CADDY_TLS=tls internal`,
имена `localhost` и `api.localhost`, `HTTPS_PORT=8443`, `HTTP_PORT=8080`,
`PUBLIC_WEB_URL=https://localhost:8443` и
`PUBLIC_API_URL=https://api.localhost:8443`, затем запустите скрипт
с отдельным `COMPOSE_PROJECT_NAME`. Сертификат локального CA Caddy
потребуется добавить в доверенные для браузера. Не используйте для этого
production-базу или production-секреты.

### Резервные копии и восстановление (deploy из исходников)

Для внешней копии на Windows без отдельного сервера выполните
`powershell -File scripts/install-local-backup.ps1`: задание «DKP staging backup»
ежедневно в 10:00 скачивает свежую копию по SSH alias `dkp-stage` в
`%USERPROFILE%\Backups\dkp-staging`, сверяет SHA-256 и хранит последние
30 проверенных копий. Ручная проверка: `powershell -File scripts/pull-backups.ps1`.
ПК должен быть включён, пользователь — вошедшим, SSH-ключ — доступным;
пропущенный запуск выполняется при следующей возможности. Целевой RPO —
24 часа при успешных ежедневных копировании на сервере и скачивании.
При выключенном ПК внешний RPO растёт до следующего успешного запуска.

Production на том же VPS создаёт копию ежедневно в 03:47 МСК в
`/opt/dkp-production/backups`. Чтобы получать проверенную копию за пределами
VPS, установите отдельное задание
`powershell -File scripts/install-local-backup.ps1 -Environment production`.
Оно скачивает комплект в `%USERPROFILE%\Backups\dkp-production` в 10:00.
Каталог доступен владельцу Windows и SYSTEM, комплект хранится 30 дней.
Задание берёт отметку последней успешной копии из
`/var/log/dkp-production-backup.log`, который пишет production-cron.
Оба файла сверяются по SHA-256 до публикации `verified.json`.
Копия старше 26 часов, сбой SSH или несовпадение хэша дают ненулевой
результат задания и статус `ERROR` в `last-run.txt`.
На компьютере владельца проверяйте `LastTaskResult` и время последней
успешной записи через `Get-ScheduledTaskInfo -TaskName 'DKP production backup'`.
При потере VPS возьмите последний проверенный комплект из этого каталога.
В нём находятся `database.dump`, `screenshots.tar.gz` и `verified.json`
с контрольными суммами и SHA API на момент скачивания.

Контрольное восстановление на staging:
`python3 scripts/verify-restore.py /opt/dkp-guild-site/backups/<UTC-время>`.
Скрипт восстанавливает БД и файлы в изолированных Docker-контейнерах без
публичных портов, проверяет SHA, вход администратора и скачивание файлов.
Он использует уже имеющийся образ API и не запускает seed/миграции.
Измеренный 2026-11-16 RTO — 7,47 с (копия и образ уже на сервере);
время восстановления потерянного VPS этим тестом не измерялось.

Ежемесячное контрольное восстановление production выполняйте с внешней
проверенной копии на компьютере с Docker и Python 3.12+.
Сопоставьте `observedServerCommit` в `verified.json` с полным SHA
опубликованного Git-тега. По истории production Deploy подтвердите, что
релиз действовал в момент снимка: `verified.json` фиксирует SHA при скачивании.
Берите digest API из архива подтверждённого релиза.
Для контрольной копии 23.11.2026 подходит `v0.4.0` (`246a7d1d13f7…`).

```powershell
py -3 scripts/verify-restore.py '<каталог проверенной копии>' --production-image '<образ API>@sha256:<digest>' --release-sha '<полный SHA тега>'
```

Скрипт сверяет SHA-256 обоих файлов перед импортом. Он восстанавливает
PostgreSQL и скриншоты во внутренней Docker-сети без опубликованных портов
и без seed или миграций. Затем проверяет health, локальный вход с временными
учётными данными, основные таблицы и скачивание всех файлов, указанных в БД.
Команда выводит возраст снимка на начало учения и время от проверки сумм до
успешной проверки API с уже загруженным образом. По завершении проверьте,
что временные контейнеры, сеть и том БД удалены.

После изменения серверной конфигурации с учётной записи оператора запустите
`powershell -File scripts/production-recovery-config.ps1 -Action Save`.
Файл `recovery-config.dpapi` в защищённом каталоге внешних копий
расшифровывается тем же профилем Windows без обращения к VPS.
На учении проверьте расшифровку через `-Action Verify`.
При реальной потере VPS `-Action Restore` создаёт
`.env.production.recovery` в том же каталоге. Перенесите его на новый VPS
без вывода содержимого, установите права 0600 и удалите распакованный файл
после переноса. DPAPI требует действующий профиль оператора Windows.

Резервную копию отдельно создаёт `sh scripts/backup-prod.sh`: `pg_dump` в
формате custom и архив тома скриншотов помещаются в `backups/<UTC-время>` с
ограниченными правами. Переменная `BACKUP_REMOTE` включает копирование через
`rsync` в заранее настроенное отдельное хранилище; ошибка копирования
означает неуспешный запуск. Для ежедневной копии на Ubuntu:

1. Установите `cron`, `rsync` и `util-linux` (для `flock`):
   `sudo apt-get install cron rsync util-linux`. На сервере хранения тоже
   нужен `rsync`. Подготовьте отдельный каталог, например
   `/srv/dkp-backups/dkp-guild-site`, и SSH-доступ к нему по ключу.
2. Настройте и проверьте `known_hosts` и SSH-ключ **root**, поскольку cron
   ниже выполняется от root. Проверьте `sudo ssh -o BatchMode=yes
dkp-backup@backup.example.net true`; ключ сервера сверяйте отдельно.
3. Скопируйте `scripts/backup-prod.cron` во временный файл, укажите реальный
   абсолютный путь checkout (в примере `/opt/dkp-guild-site`) и
   `BACKUP_REMOTE`. Установите его: `sudo install -o root -g root -m 644
<файл> /etc/cron.d/dkp-guild-backup`, затем `sudo systemctl enable --now
cron`. Копия запускается ежедневно в 03:00 **по часовому поясу хоста**;
   `timedatectl` показывает его. `flock` предотвращает наложение
   cron-запусков.
4. До ожидания расписания выполните вручную:
   `sudo env BACKUP_REMOTE=dkp-backup@backup.example.net:/srv/dkp-backups/dkp-guild-site
sh /opt/dkp-guild-site/scripts/backup-prod.sh`. Убедитесь, что оба файла
   появились на другом сервере. Проверяйте код возврата и
   `/var/log/dkp-guild-backup.log`; настройте оповещение при ошибках
   и ротацию этого лога средствами хоста.
5. На отдельном хранилище настройте lifecycle удаления копий старше 30
   дней. Для обычного Linux-хоста добавьте в crontab пользователя хранилища
   (`crontab -e`) ежедневную очистку **выделенного каталога этой системы**:

   ```cron
   0 5 * * * find /srv/dkp-backups/dkp-guild-site -mindepth 1 -maxdepth 1 -type d -name '20??????T??????Z' -mtime +29 -exec rm -rf -- {} +
   ```

   Сначала проверьте выборку той же командой с `-print` вместо
   `-exec ... +`. Локальные копии самостоятельно не удаляются; следите
   за свободным местом или примените такую же политику к выделенному
   каталогу `backups`. Для релизного установщика вместо этого используется
   `dkp backup setup` с собственным systemd-таймером; два расписания
   одновременно не настраивайте.

Не реже раза в месяц проверяйте восстановление **в отдельной тестовой
базе**: создайте чистую БД, выполните `pg_restore --no-owner
--no-privileges -d <test_db> database.dump`, распакуйте `screenshots.tar.gz`
в отдельный каталог и проверьте запуск приложения и файлы. Не
восстанавливайте поверх рабочей БД без плана остановки и отдельной
актуальной копии.

### Мониторинг доступности (Uptime Kuma)

Uptime Kuma работает на том же VPS отдельным Compose-проектом
`dkp-monitoring` (`docker-compose.monitoring.yml`): проверяет сайт каждые
60 секунд и отправляет оповещение при аварии и отдельное — при
восстановлении. Порты наружу не публикуются: панель доступна только через
edge-прокси на `https://status.suneclipse.ru` (вход — пароль администратора
Kuma), база и история проверок лежат в томе
`dkp-monitoring_uptime-kuma-data`. Проект не занимает блокировку деплоя и
не мешает резервным копиям.

**Установка** — файлы в `/opt/dkp-monitoring`, по образцу `/opt/dkp-edge`:
скопируйте из checkout `docker-compose.monitoring.yml` и каталог
`scripts/monitoring/`, затем:

```sh
cd /opt/dkp-monitoring
cp .env.monitoring.example .env.monitoring && chmod 600 .env.monitoring
docker compose --env-file .env.monitoring -f docker-compose.monitoring.yml up -d --wait
sh scripts/monitoring/kuma-setup.sh apply --dry-run   # план
sh scripts/monitoring/kuma-setup.sh apply
```

В `.env.monitoring` задайте пароль администратора панели (например,
`openssl rand -base64 24`) и каналы оповещений; файл хранится только на
сервере. Сценарий при первом запуске создаёт администратора и приводит
мониторы и уведомления к окружению; повторный запуск ничего не меняет, а
убранные из окружения мониторы и каналы удаляет. `UPTIME_KUMA_DB_TYPE` в
Compose задаёт встроенную MariaDB, поэтому мастер выбора базы в браузере не
появляется.

**Панель.** Блок `status.suneclipse.ru` уже есть в `Caddyfile.edge`, а
`docker-compose.edge.yml` подключает прокси к сети `dkp-monitoring_default`.
Чтобы применить, скопируйте оба файла в `/opt/dkp-edge` и выполните там
`docker compose -f docker-compose.edge.yml up -d --wait`: контейнер прокси
пересоздаётся, оба сайта закрыты несколько секунд. Проект мониторинга должен
быть запущен раньше — иначе edge не найдёт сеть. Сертификат для поддомена
Caddy получает сам; DNS должен указывать на сервер напрямую, без
проксирования Cloudflare. Вход в панель — учётная запись из
`.env.monitoring`.

**Мониторы production.** Общий порог — константа `POLICY` сценария.

| Монитор                       | Что проверает                                                                                                                           |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `Прод: API — здоровье`        | `GET /api/health`: ответ `status ok` **и** `db up` (одна JSON-проверка); срок TLS-сертификата сайта — предупреждения за 21, 14 и 7 дней |
| `Прод: сайт — страница входа` | `/` отвечает кодом 2xx. Это web-контейнер: без API страница всё равно открывается, поэтому отказ API ловит предыдущий монитор           |
| `Прод: WebSocket (аукцион)`   | рукопожатие `/api/socket.io`: соединение WebSocket устанавливается и закрывается кодом 1000                                             |

Порог: проверка раз в 60 секунд; после неудачи повторы через 60 секунд;
тревога на четвёртой подряд неудачной проверке — через три минуты после
первой неудачи, то есть не позже четырёх минут от начала отказа.
Восстановление — отдельным сообщением; затяжная авария повторяется
сообщением раз в два часа. Штатный деплой останавливает API на время
остановки, снимка, миграций, seed и запуска: в двух релизах (v1.2.0, v1.3.0)
между началом снимка и запуском нового контейнера проходило 12–13 секунд, а
весь простой — десятки секунд. До тревоги нужны непрерывные три минуты,
поэтому деплой её не даёт; релиз с остановкой API дольше трёх минут даст
одно оповещение и одно восстановление.

Мониторы стенда включает `KUMA_STAGING_HOST`; по умолчанию они не шлют
оповещений, `KUMA_STAGING_NOTIFICATIONS=1` разрешает.

**Оповещения.** Основной канал — личное сообщение от бота сайта в Discord.
Вебхуки Discord пишут только в каналы, поэтому Kuma шлёт вебхук
ретранслятору `alert-relay` в том же Compose-проекте, а он пишет от имени
бота получателям из `ALERT_DISCORD_USER_IDS`. Ретранслятор живёт отдельно
от API сайта намеренно: оповещение «API не отвечает» не должно зависеть от
самого API. Канал включается профилем `alerts` в `.env.monitoring`
(`COMPOSE_PROFILES=alerts`, секрет `ALERT_RELAY_TOKEN`, токен бота
`ALERT_BOT_TOKEN` — тот же, что у приложения). Дополнительно можно задать
вебхук канала Discord или почту (SMTP); без канала панель работает молча.

Доставку проверяют `kuma-setup.sh test-notification` (или кнопкой Test в
панели), а саму тревогу — тестовым сбоем на стенде, не на production.
Мониторы стенда по умолчанию выключены; на время опыта задайте
`KUMA_STAGING_HOST=stage.suneclipse.ru` и `KUMA_STAGING_NOTIFICATIONS=1`,
выполните `apply`, а после проверки верните пустой `KUMA_STAGING_HOST`:

```sh
docker stop dkp-guild-site-api-1      # и параллельно: sh scripts/monitoring/kuma-setup.sh status --watch 300
docker start dkp-guild-site-api-1
```

`kuma-setup.sh status` показывает последние проверки без браузера.

**Обновление** — смените тег в `docker-compose.monitoring.yml` на свежий
стабильный, скопируйте файл на сервер и повторите `up -d --wait` и `apply`.
Kuma при запуске новой версии мигрирует свою базу, возврата к прежнему тегу
нет.

**Потеря VPS.** Данные Kuma в резервные копии не входят: панель, мониторы и
ретранслятор восстанавливаются установкой из этого раздела, теряется только
история проверок.

**Внешний пробник.** Отказ самого VPS или блокировку адреса на пути от
пользователей мониторинг на этом же сервере не заметит, поэтому workflow
`Uptime probe` по расписанию — каждые 15 минут — проверяет
`https://suneclipse.ru/api/health` с зондами Globalping в РФ и Латвии
(`scripts/monitoring/external-probe.mjs`). Сайт считается доступным, только
если из каждой страны зонд получил ответ `200` с `status ok` и `db up`. Разовый
сбой зонда аварией не считается — только неудача трёх попыток подряд. Авария —
это неудача запуска workflow: GitHub присылает письмо о неудавшемся
запланированном запуске (зависит от настроек уведомлений GitHub), сводка
зондов — в Summary запуска. Интервал — ориентировочный: GitHub может
задерживать запланированные запуски на десятки минут в часы пик, поэтому на
пробник не полагаются там, где важна минутная своевременность. API Globalping
используется без токента, с лимитами для анонимных запросов. Вне расписания:
Actions → Uptime probe → Run workflow.

### Проверка инфраструктуры без сервера

Проверка выполняется workflow `Infrastructure` при PR, push в `main`
и вручную. Он проверяет все workflow через actionlint, валидирует Compose,
синтаксис shell-скриптов, тестирует порядок деплоя и обработку ошибок
с подставным Docker, затем собирает оба production-образа. После сборки он
поднимает изолированный стек с `tls internal`, проверяет HTTPS сайта
и `/api/health`, наличие снимка БД/скриншотов и удаляет только тестовые
контейнеры и тома. Отдельная задача `Uptime Kuma provisioning` поднимает
настоящую Kuma во временном проекте и прогоняет сценарий настройки (план,
два применения, смена окружения, статус) с адресами мониторов в `.invalid` —
без обращения к настоящему сайту; затем включает ретранслятор оповещений
с заглушкой Discord и проверяет, что пробное сообщение дошло в «личку».
Локальный эквивалент (из корня checkout, нужны Docker, curl, Node.js 22+
и Python 3; порты 18080/18443 должны быть свободны):

```sh
docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:1.7.12 -color
docker compose --env-file .env.production.example -f docker-compose.prod.yml config --quiet
docker compose --profile alerts -f docker-compose.monitoring.yml config --quiet
sh -n scripts/deploy-prod.sh
sh -n scripts/backup-prod.sh
sh -n scripts/smoke-prod.sh
sh -n scripts/monitoring/kuma-setup.sh
sh -n scripts/monitoring/smoke-kuma.sh
node --test scripts/monitoring/*.test.mjs
python3 -m unittest discover -s scripts -p 'test_*.py' -v
sh scripts/smoke-prod.sh
sh scripts/monitoring/smoke-kuma.sh
```

Проверка не выполняет SSH-деплой, не читает production secrets и не меняет
рабочую БД. На пустой БД используйте `scripts/deploy-prod.sh`: обычный
`compose up` намеренно не применяет миграции без предварительной копии.
Скрипты deploy и backup принимают `PRODUCTION_ENV_FILE` (по умолчанию
`.env.production`); smoke использует временный файл, не заменяя рабочий env.

## Контракт API (Swagger / OpenAPI)

При запущенном API интерактивная документация доступна на
[http://localhost:3001/docs](http://localhost:3001/docs), JSON-контракт — на
[http://localhost:3001/openapi.json](http://localhost:3001/openapi.json)
(для Docker используйте свой `SITE_API_PORT`). JSON можно импортировать
в Postman или генератор клиента. Документ строится из текущих маршрутов
NestJS, схемы запросов — из общей Zod-валидации; описания ответов находятся
в `apps/api/src/openapi`.

Для **Try it out** сначала войдите в том же браузере через
`/auth/discord` или выполните `POST /auth/admin/login` в Swagger.
Браузер отправляет httpOnly-cookie `dkp.sid` автоматически. Успешность
резервного входа проверяйте по `ok`, затем вызовите `GET /auth/me`.
Действия меняют реальные данные текущего окружения. Тестовый вход
описывается только при `AUTH_TEST_MODE=true`.

## Вход через Discord (OAuth2)

1. Создайте приложение на <https://discord.com/developers/applications>.
2. В **OAuth2 → Redirects** добавьте URI вида
   `http://localhost:<порт API>/auth/discord/callback`
   (порт тот, на котором API реально доступен из браузера:
   `3001` для `pnpm dev`, `SITE_API_PORT` для Docker).
3. В `apps/api/.env` заполните:
   ```env
   DISCORD_CLIENT_ID=...
   DISCORD_CLIENT_SECRET=...
   DISCORD_CALLBACK_URL=http://localhost:3001/auth/discord/callback
   SESSION_SECRET=...   # node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```
4. Новые пользователи входят как непривязанные аккаунты и отправляют
   анкету — Глава/Админ подтверждает её на странице «Заявки». Первый
   случайный вход **не назначает Главу**; Админ назначает его через смену
   ранга в разделе «Состав» после одобрения участника (PLAN.md 12.12).
5. Резервный вход админа (если Discord недоступен): `ADMIN_LOGIN` /
   `ADMIN_PASSWORD` в том же `.env`. Без параметров Discord этот вход
   остаётся доступен. При частично заполненных параметрах Discord отключён;
   `/auth/providers` возвращает только `{ "discord": false }`, оба маршрута
   OAuth отвечают 503 с пояснением. После изменения настроек перезапустите
   API.

При `pnpm dev` адрес `/api` проксируется Next.js на `localhost:3001`.
Явный `NEXT_PUBLIC_API_URL` в `apps/web/.env.local` по-прежнему
поддерживается; локальный Docker Compose сохраняет прямой адрес API
и настройку его порта.

Если Discord после логина «не возвращает на сайт» — почти всегда это
несовпадение `DISCORD_CALLBACK_URL` с фактическим портом API (проверьте
адресную строку) или отсутствие этого URI в списке Redirects приложения.

## Тестирование

**Юнит-тесты** — `pnpm test` (обязательны в каждом PR, CI гоняет их же).

**Тестовый вход без Discord** (e2e, ручная проверка ролей на staging):

```bash
pnpm db:seed:test                          # создать test-leader/test-officer/test-member(-2)
# в apps/api/.env: AUTH_TEST_MODE=true     # и перезапустить API
curl -c cookies.txt -d '{"username":"test-officer"}' localhost:3001/auth/test-login
curl -b cookies.txt localhost:3001/auth/me # сессия с рангом OFFICER
```

Без `AUTH_TEST_MODE=true` ручка отвечает 404. В production приложение
с включённым флагом **не стартует** (fail-fast). Тестовые пользователи
создаются только с никами `test-*`, за реальных людей войти нельзя.

### Приватные скриншоты профиля

Файлы PNG, JPG/JPEG и WebP до 10 МБ загружаются через `POST /screenshots`
(`multipart/form-data`, поле `file`). Доступ к `GET /screenshots/:id`
проверяется по сессии: владелец, Глава или Админ. Статической публичной
раздачи нет. В обычной разработке каталог —
`apps/api/uploads/screenshots` (или `SCREENSHOT_DIR`). При `pnpm site:up`
файлы сохраняются в отдельном томе `screenshot-data`; его нужно включать
в резервную копию вместе с PostgreSQL. После обновления схемы примените
миграции к локальной БД перед запуском API. В CI миграции и конкурентные
сценарии приёма и выборки дашборда проверяются на отдельной PostgreSQL
`dkp_test`.
