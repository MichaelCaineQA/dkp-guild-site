# Архитектура и ограничения

Перенесено из корневого AGENTS.md. Требования и решения имеют единственный
источник — [PLAN.md](../PLAN.md); этот файл помогает применять их при разработке.

## Карта репозитория

- `apps/web` — Next.js, App Router, TypeScript strict.
- `apps/api` — NestJS; Prisma-схема: `apps/api/prisma/schema.prisma`.
  Справочник предметов аукциона — модуль `apps/api/src/items` (issue #92);
  дроп и создание лота в проведении ивента — `apps/api/src/loot` (issue #93);
  ставки и закрытие лотов — следующие задачи этапа 2 (#94/#95).
- `packages/shared` — общие типы, zod-схемы и чистая логика ядра.
- `.github/workflows/ci.yml` — проверки CI.
- `installer/` — установщик релизного Compose для одного домена, изолированного
  проекта `dkp-guild` и состояния `/var/lib/dkp-guild`; упаковка по тегу —
  `.github/workflows/release.yml` и `scripts/release/package.sh`. Для файлов
  релиза используются digest образов и контрольные суммы. Реальную приёмку на
  чистой VM нужно провести отдельно (issue #75).
- Production web использует same-origin `/api`: Caddy убирает префикс,
  dev — прокси Next.js на :3001. Локальный Docker Compose сохраняет явный
  `NEXT_PUBLIC_API_URL`. Discord необязателен: `/auth/providers` возвращает
  доступность без секретов; при пустой/частичной конфигурации OAuth закрыт,
  резервный вход администратора работает. После изменения env API перезапускают.
- Название и прозрачный герб хранятся в `Guild` в PostgreSQL; герб попадает
  в резервную копию базы, отдельный каталог для него не нужен. Проверка файла —
  декодирование `sharp` в настройках; шапка обновляется по `guild:changed`.

## Обязательные ограничения

1. **Журнал ДКП append-only:** записи `DkpEntry` не правятся и не удаляются;
   исправление — новая запись. Баланс = сумма записей (`computeBalance`
   в `packages/shared`). Источник: PLAN.md 2.2, 3.
2. **Чек-ин коды хранятся только хэшем.** Сам код видят Глава, Админ,
   назначенный РЛ и создатель ивента с текущим рангом Офицер; коды не пишутся
   в аудит, только факт генерации.
   Источник: PLAN.md 2.2, 2.6, 2.9, 3.
3. **Игровые правила — в настройках, не константами в коде.** Платы, наценки,
   окна кодов, длительности лотов — в `Setting`. Новые настройки добавляй
   вместе с zod-схемой в `packages/shared`; источник ограничений и дефолтов —
   `SETTINGS_REGISTRY` / `SETTING_DEFAULTS`. Исключение из PLAN.md 2.12:
   якорь и длительности фаз игрового цикла хранятся на `Guild`.
4. **Любое ручное действие** (отметки посещения, назначение победителя лота,
   смена рангов) пишет `AuditLog` с комментарием. Изменения своего профиля
   тоже аудируются. Источник: PLAN.md 2.9, 12.
5. **Время:** календарные даты — UTC в БД, отображение в таймзоне игрока;
   день виджета «События дня» — по Москве. Таймлайн внутриигровых суток —
   единая для всех шкала сервера. Расчёт фазы — `getGamePhase`
   в `packages/shared`, якорь — настройка гильдии. Источник: PLAN.md 2.1.
6. **Логика ядра** (ДКП, права, окна кодов, анти-снайп) живёт
   в `packages/shared` и покрывается юнит-тестами **в том же PR**.
7. **UI — только русский язык.**
8. **Приватность проверяется на сервере:** ограничения GS/скриншотов действуют
   на API, файлы, скачивание и аудит; скрыть поле в UI недостаточно.
   Точная матрица доступа — PLAN.md 2.5–2.6.

## При изменении UI

Прочитай [UI-справочник](../ui/README.md) и соответствующий экран;
он описывает представление, требования остаются в PLAN.md.
Устройство палитры и компонентов — в
[DESIGN.md](../../apps/web/DESIGN.md): палитра в `app/globals.css`,
визуальные примитивы в `components/ui`, страницы связывают данные и действия.
После правок UI прикладывай скриншот в PR.
