# Архитектура и ограничения

Перенесено из корневого AGENTS.md. Требования и решения имеют единственный
источник — [PLAN.md](../PLAN.md); этот файл помогает применять их при разработке.

## Карта репозитория

- Еженедельное сгорание (#342) выполняет `DkpDecayScheduler` с понедельника
  00:00 МСК. Сохранение `dkp.weeklyDecayPct` записывает ставку для следующей
  границы недели в `DkpDecayRate`. При рестарте сканер обрабатывает пропуски
  по порядку. `DkpDecayRun` и записи `WEEKLY_DECAY` добавляются одной
  транзакцией. Сумма считается из журнала до границы, запись датируется
  границей недели. В статистике списания входят в операции «Без ивента».

- Доставка Discord (#278): `discord-notifications/discord-outbox.ts` пишет
  уведомление по стабильному ключу внутри транзакции вызывающей операции.
  Отправитель использует PostgreSQL `DiscordNotification` и общий
  `DiscordDeliveryGate` для сериализации воркеров и сохранения задержки 429;
  без `DISCORD_BOT_TOKEN` и `DISCORD_GUILD_ID` он не запускается. Настройки
  каналов и записи очереди привязаны к ID сервера окружения; чужие записи
  не отправляются. Повтор после потери ответа
  использует тот же nonce, но Discord ограничивает окно дедупликации.
  Настройки #279 хранятся в `Setting` под `discord.channels`; доступ только
  с `settings.manage`, каналы проверяются через Discord и запись аудируется.
  Проверка доставки идёт по сохранённым каналам, поэтому в web кнопка
  «Проверить сохранённый канал» недоступна, пока поле отличается от
  сохранённого значения (#315, PR #323).
  Канал отсутствий может быть общим — тем же ID, что у анонсов, напоминаний
  или итогов лотов (#325): отдельный закрытый канал и подтверждение
  закрытости не требуются, `absenceAccessConfirmed` в `PUT /settings/discord`
  необязателен и игнорируется (его может прислать прежняя вкладка страницы).
  Сохранённые каналы работают без миграции: подтверждение нигде не хранилось.
  Анонсы
  #280 создаются в транзакции ивента; очередь хранит ID событий и формирует
  текст при отправке, исключая отменённые, удалённые и начавшиеся события.
  Серия делится на сообщения до 25 дат и лимита Discord с паузой между ними.
  Напоминания #282: сканер каждые 5 секунд восстанавливает запланированные
  ивенты внутри окна `discord.reminderMinutes` (дефолт 15), ключ включает ID
  время начала и Discord-сервер. Старые ключи распознаются без смены nonce,
  только если их `guildId` совпадает с окружением (#291). Перенос создаёт новый
  ключ, изменение N пересчитывается до
  отправки; при создании внутри окна напоминание ставится сразу. Отмена,
  удаление, запуск и наступившее время отменяют ожидающую доставку.
  Заявки #283 из формы периода и отказа от ивента ставятся в очередь в той же
  транзакции; отправитель выбирает только ник, период и название ивента,
  причину не читает и не передаёт. Перед отправкой проверяется ACTIVE и
  текущий канал отсутствий; ручная корректировка итогов не является заявкой.
  Итоги лотов #281 сохраняются в очередь вместе с выдачей или отменой как
  снимки публичных данных без причины ручного действия. `DiscordLotCursor`
  связывает очередные результаты одного лота в рамках Discord-сервера:
  исправление ожидает предыдущую
  публикацию или её окончательный отказ, сохраняя порядок при повторах.
- Основа статистики (#212): `packages/shared/src/statistics.ts` задаёт
  московский период, фильтры и DTO; `apps/api/src/statistics` читает данные
  в одном срезе PostgreSQL. Переводы восстанавливаются на начало ивента;
  участие в прошлом помечается `NO_HISTORICAL_DATA`, поскольку точной полной
  истории блокировок и разблокировок нет. Без записей о переносе текущая
  принадлежность не используется как доказательство прошлого состава.
  Участники без Attendance сохраняются
  как кандидаты; факты без ивента возвращаются отдельной категорией и не
  получают историческую команду или тип ивента.
- Отчёты статистики — шесть эндпоинтов `GET /statistics*` на одном контроллере
  с правом `members.view_roster` и общими фильтрами `statisticsQuerySchema`:
  `""` — основа (#212), `/attendance` — посещаемость (#213,
  `attendance-statistics.ts`: половины `(C/2)/N×100%`, уважительные
  отсутствия вне знаменателя), `/activity` — активность (#214,
  `activity-statistics.ts`: одна принятая отметка = одно посещённое событие,
  пик по бакетам Москвы 7×24 с явными нулями, `events` — число разных
  ивентов, участники его не умножают; историческая команда — в деталях
  участий), `/dkp` — ДКП (#215, `dkp-statistics.ts` в shared и API):
  движения периода по `DkpEntry.createdAt` с показателями раздельно
  (earned = CHECKIN_EARN+MANUAL_EARN, spent = AUCTION_SPEND фактов журнала,
  adjustments — чистая ADJUSTMENT со знаком: положительная корректировка
  не заработок); поздняя корректировка входит в период записи, команда —
  на дату ивента; полный баланс `members[].balance` — вся история до
  `balanceAsOf` без ограничений фильтров типа/PvE–PvP (DTO сообщает
  `balanceIgnoresFilters`, UI/CSV обязаны подписать); категория
  «Без ивента» без атрибуции и фильтров, в итоги не подмешивается.
  `/loot` — лут (#216, `loot-statistics.ts` в shared и API): два разных
  факта — «Выпало» (период по дате дропа; доли предметов целыми процентами
  с суммой ровно 100 методом наибольших остатков; нераспределённые
  выпадения остаются здесь, `lotStatus` объясняет отсутствие выдачи)
  и «Получено» (только `LootAward` по дате выдачи; `finalPrice` — фактическое
  списание без пересчёта по текущим ценам; группировки по игроку/паку/КП —
  число предметов и сумма ДКП); топ обзора со строкой «Остальное»
  (знаменатель — вся выборка «Выпало», `LOOT_TOP_ITEMS_LIMIT`=5); команда
  выдачи — на дату ивента (переводы позже не переносят), у дропа — область
  ивента на его дату; хранилище — отдельная категория «Без ивента»
  в обоих представлениях, в выборку топа не входит.
  `/gear-score` — свежесть GS (#217, `gear-score-statistics.ts` в shared
  и API): защищённый отчёт только Главе/Админу — сервис первым делом
  проверяет `canViewGuildGearScore` (лидерство КП/пака и РЛ не входят
  в actor, план 2.5), остальные ранги получают 403, а общие отчёты GS-полей
  не содержат. Срез `asOf` = min(конец периода, момент отчёта): состав
  и последние записи со скрином фиксируются на него, новые загрузки прошлый
  отчёт не меняют; категории FRESH/STALE/MISSING — по правилу профиля
  (последняя запись со скрином, строго старше порога; записи без скрина
  не считаются). Команды — исторические на срез (как `statisticsEventMembers`,
  NO_HISTORICAL_DATA не означает отсутствия скрина), фильтры КП/пак
  консервативно пропускают неизвестную историю; ивентных фактов у среза нет,
  поэтому eventTypeId/mode валидируются, но не влияют и перечисляются
  в `snapshotIgnoresFilters` (UI/CSV обязаны подписать). Порог
  `profile.gearScoreStaleDays` и asOf возвращаются явно; значений GS в отчёте
  нет — только категории и дата последнего скрина.

- Состав (#345): `Member.directKpId` используется для участников КП без пака.
  У участников с паком КП по-прежнему берётся из `Pack.kpId`.
  `OrgService` проверяет текущий ранг, лидера КП и принадлежность игрока
  в serializable-транзакции переноса. `MemberPackHistory` хранит обе стороны
  переноса, включая прямую КП. При чтении состава ивента, доступе лидера
  КП к данным и восстановлении состава для статистики учитываются обе
  формы членства. Источник правил — PLAN.md 2.6 и 2.7.
- Бонус РЛ (#340) записывается как `RAID_LEAD_BONUS` в журнал ДКП.
  `dkp/raid-lead-bonus.ts` сверяет фактические записи `CHECKIN_EARN` и уже
  начисленный бонус в транзакциях завершения ивента и поздних отметок.
  `Event.raidLeadBonusEnabled` включается при переходе в `FINISHED`, чтобы
  корректировки исторических ивентов не выдавали бонусы задним числом.
- Чек-ин кода и ручной старт/завершение ивента (#318, план 2.2, решение 23):
  окно кода открывается только кнопкой, расписание ивента на него не влияет.
  `POST /events/:id/status` с `RUNNING` или `FINISHED` одной serializable-
  транзакцией меняет статус, пишет аудит и через хук
  `EventsService.onEventCodeLaunch` запускает окно своей фазы
  (`apps/api/src/checkin/launch.ts`: окно от момента нажатия на
  `checkin.windowSec`; уже открытое окно не перевыпускает, пройдшее заменяет
  новым кодом — так завершают ивенты с кодом от прежней генерации по
  расписанию). Хук ставит `attachCheckInLaunch` из `CheckInModule`, его же
  вызывают database-спеки. Чистые правила окон — `manualWindowBounds`,
  `activeCheckInPhase`, `checkInPhaseView` в shared `checkin.ts`. Ленивой
  генерации по времени и эндпоинта `checkin/end-early` больше нет.
  `CheckInService` собирается контроллером на запрос и знает только доли
  платы; `CHECKIN_ENC_KEY` — один модуль `checkin/enc-key.ts` на процесс.
  Финальное окно действует и при статусе `FINISHED`, поэтому чек-ин закрыт
  только для `CANCELLED`. Статус в `changeStatus` перечитывается в
  транзакции: одновременные нажатия двух управляющих дают один код, второй
  получает 409; `onEventFinished` (авто-отметка отсутствий) выполняется
  после коммита, как и до #318. Web: `ConfirmDialog` (`ui/modal.tsx`), тексты
  подтверждений — `components/event-actions.ts`; карточка держит статус после
  нажатия сама (`statusOverride`), пока родитель не перечитал ивент, и сразу
  перечитывает код (`key={codesVersion}`). На `/schedule` страница при каждом
  `onChanged` ставит `pending` и убирает карточку — та перемонтируется, и её
  локальное состояние (сообщение, `statusOverride`) теряется: рассчитывать
  можно только на новый `event` от родителя. Дашборд и окна статистики
  карточку не пересоздают. После `FINISHED` дроп и лоты на
  ивент не фиксируются (план 2.6) — подтверждение завершения об этом говорит.
- `apps/web` — Next.js, App Router, TypeScript strict.
- `apps/api` — NestJS; Prisma-схема: `apps/api/prisma/schema.prisma`.
  Справочник предметов аукциона — модуль `apps/api/src/items` (issue #92);
  `Item.isArchboss` — отметка «Архибосс» (#208, решение 21): словарь
  редкостей Редкий/Эпический 1–3/Легендарный (архибосс — качество
  Эпический 1 или 2, отдельного качества нет). У участника **два** желаемых
  предмета: `preferredItemId` (без отметки) и `preferredArchbossItemId`
  (только отмеченные; prev/changedAt — как у обычного, кулдаун свой).
  Скидка при ставке и `myPreferred` — по любому из двух желаний; снимок
  `bidderProfiles` хранит оба поля (старые JSON — без archboss-поля,
  нормализуются в null). Сервер 400-ит пересечение списков.
  дроп и создание лота в проведении ивента — `apps/api/src/loot` (issue #93);
  ставки с заморозкой и анти-снайпом — `apps/api/src/bids` (issue #94);
  приём ставки сначала блокирует строку лота (`SELECT FOR UPDATE`, #161),
  затем читает данные и серверное время. `serializable()` повторяет P2034
  и raw SQL P2010 с SQLSTATE 40001/40P01; остальные raw-ошибки не повторяет.
  скидка за предпочитаемый предмет (#101, PR #125): на `Member` хранятся
  `preferredItemId` + `prevPreferredItemId`/`preferredItemChangedAt` и
  `prevCombatRole`/`combatRoleChangedAt` — прежние поля сохраняются для
  совместимости. С #169 роль и предпочтение каждого существующего участника
  записываются в `Auction.bidderProfiles` (JSON) при создании лота одной
  serializable-транзакцией с аудитом; ставки и `myPreferred` читают этот
  неизменяемый снимок. Повторные смены, продления и удаление предмета
  снимок не меняют. Миграция старых лотов использует доступные prev-поля;
  утраченную историю нескольких старых смен восстановить нельзя. Поведение
  вступивших после открытия лота оставлено прежним (PLAN 6 требует уточнения).
  `bidFullCost`
  в shared: сначала наценка, затем от наценной цены скидка, ceil;
  `Auction.discountPct` — снимок настройки при создании лота, `Bid/LootAward
.discountPct` — применённые. Смена роли/предмета — кулдаун
  `auction.profileChangeCooldownDays` (409 с датой), первый выбор сразу;
  удаление предмета — FK SetNull (поле очищается у всех); настройки
  `auction.preferredItemDiscountPct`/`foreignClassMarkupPct` — дефолты 10/10,
  обе ≤100%. Список лотов отдаёт viewer-специфичное `myPreferred` по снимку;
  закрытие лотов и автосписание — `apps/api/src/auction-close` (issue #95):
  свипер каждые `AUCTION_CLOSE_INTERVAL_MS` мс (дефолт 1000, 0 — выкл)

1. **Журнал ДКП append-only:** записи `DkpEntry` не правятся и не удаляются;
   исправление — новая запись. Баланс = сумма записей (`computeBalance`
   в `packages/shared`). Источник: PLAN.md 2.2, 3.
2. **Чек-ин коды хранятся только хэшем.** Сам код видят Глава, Админ,
   любой Офицер и назначенный РЛ ивента; коды не пишутся
   в аудит, только факт генерации.
   Источник: PLAN.md 2.2, 2.6, 2.9, 3.
3. **Игровые правила — в настройках, не константами в коде.** Платы, наценки,
   окна кодов, длительности лотов — в `Setting`. Новые настройки добавляй
   вместе с zod-схемой в `packages/shared`; источник ограничений и дефолтов —
   `SETTINGS_REGISTRY` / `SETTING_DEFAULTS`. Исключение из PLAN.md 2.12:
   якорь и длительности фаз игрового цикла хранятся на `Guild`.
4. **Любое ручное действие** (отметки посещения, назначение победителя лота,
   смена рангов) пишет `AuditLog` с комментарием. Изменения своего профиля
   тоже аудируются. Источник: PLAN.md 2.9, 12.
5. **Время:** календарные даты — UTC в БД, отображение в таймзоне браузера
   устройства (решение 20); таймзона профиля (IANA) — только прайм-тайм и
   фильтр «Свободен сейчас»; день виджета «События дня» — по Москве.
   Таймлайн внутриигровых суток — единая для всех шкала сервера.
   Расчёт фазы — `getGamePhase`
   в `packages/shared`, якорь — настройка гильдии. Источник: PLAN.md 2.1.
6. **Логика ядра** (ДКП, права, окна кодов, анти-снайп) живёт
   в `packages/shared` и покрывается юнит-тестами **в том же PR**.
7. **UI — только русский язык.**
8. **Приватность проверяется на сервере:** ограничения GS/скриншотов действуют
   на API, файлы, скачивание и аудит; скрыть поле в UI недостаточно.
   Точная матрица доступа — PLAN.md 2.5–2.6.

[DESIGN.md](../../apps/web/DESIGN.md): палитра в `app/globals.css`,
