# Известные проблемы и ловушки

Проверено по документации 2026-11-08. Это не список открытых багов приложения:
актуальные задачи и статусы ведутся в GitHub Issues. Ниже отдельно отмечены
расхождения текстов и документированные симптомы окружения; воспроизведение
не подразумевается, если оно явно не указано.

## Ставки: быстрые повторы при задержанном COMMIT (#161)

- Источник: #161, PR #201, управляемое воспроизведение на PostgreSQL 16,
  проверено 2026-11-16. При задержке видимости COMMIT победителя три повтора
  равной ставки могли читать прежний снимок и получать P2034 на `INSERT Bid`;
  после исчерпания повторов сервис возвращал 409 вместо предметного 400.
- Исправление: в начале транзакции ставки блокируется строка лота через
  `SELECT FOR UPDATE`. Конкурент дожидается завершения победителя;
  сериализуемый повтор перечитывает ставку. Время проверяется после ожидания.
  Raw SQL отдаёт SQLSTATE 40001/40P01 внутри P2010 — общий helper повторяет
  эти ошибки, но не произвольные P2010. Лимит в три попытки сохранён.
- Повторная проверка: шаг CI `PostgreSQL delayed commit regression` в
  `.github/workflows/ci.yml`, тест `bids/bids-commit.database.spec.ts`.
  Он использует отдельный сервер с `synchronous_standby_names=dkp_bid_commit_test`
  и `synchronous_commit=off`; URL передаётся в `BIDS_COMMIT_TEST_DATABASE_URL`.
  Только сессия победителя включает ожидание реплики; барьер `SyncRep`
  освобождается через `pg_cancel_backend`, не откатывая локальный COMMIT.
- Это способ управляемо задержать фиксацию, а не утверждение о наличии
  синхронной реплики в исходном CI. Общую локальную БД тест не перенастраивает.
  На коде без блокировки тест воспроизводимо получает 409; с ней — 400,
  одну ставку и одну запись аудита без изменений журнала проигравшего.

## Windows: порты Docker заняты или зарезервированы

- Источник: README.md, «Вариант A», блок «Если порты заняты/заблокированы».
- Симптом: `ports are not available` / `EACCES`; возможна резервация WinNAT.
- Диагностика: `netsh interface ipv4 show excludedportrange protocol=tcp`.
- Документированный обход: в корневом `.env` согласовать `SITE_WEB_PORT`,
  `SITE_API_PORT`, `NEXT_PUBLIC_API_URL` и `WEB_URL`; также обновить
  `DISCORD_CALLBACK_URL` и Redirects в Discord. Пример портов в README: 3080/3081.
- В этой ревизии не воспроизводилось; перед изменением окружения проверь
  фактические порты и текст ошибки.

## VPS недоступен из РФ без VPN

- Источник: диагностика 2026-11-08 (185.199.158.59) и 2026-11-09
  (103.80.87.37), подтверждено внешними проверками check-host.net и
  globalping: из дата-центров РФ и из-за рубежа — OK, из абонентских
  сетей РФ (МТС, Mediasoft, Letit у владельца) — timeout по TCP и ICMP.
- Оба IP в публичном реестре РКН отсутствуют — это «тихая» блокировка
  на ТСПУ по /32, характерная для детекции VPN; соседние адреса VDSka NL
  заблокированы выборочно. Смена IP внутри NL-площадки не помогает:
  103.80.87.37 выдан 2026-11-08 уже заблокированным.
- Обход: сайт завёрнут за Cloudflare (2026-11-09, suneclipse.ru и
  поддомены в режиме Proxied, SSL Full (strict)). SSH к origin — только
  через VPN, т.к. реальный IP остаётся заблокированным.
- Остаточная проблема: TSPU провайдера подделывает ответы на QUIC
  (UDP/443): «ответ» прилетает за ~2 мс при TCP RTT 15–26 мс — браузер
  пробует HTTP/3, запросы висят в pending 10–15 с до отката на TCP.
  Лечится отключением HTTP/3 в панели Cloudflare (Network → HTTP/3)
  либо chrome://flags → QUIC у пользователя.
- SSH: парольная аутентификация отключена 2026-11-08
  (`/etc/ssh/sshd_config.d/60-dkp-hardening.conf`), вход root только по
  ключу `~/.ssh/id_ed25519` с машины владельца. Пароль root от SSH больше
  не принимается; смена пароля в ОС на SSH-доступ не влияет.
- Повторная проверка: `ssh -i ~/.ssh/id_ed25519 root@103.80.87.37`
  через VPN; `curl -sI https://stage.suneclipse.ru` → `Server: cloudflare`;
  после фикса QUIC заголовок `alt-svc` не должен содержать `h3`.

## Ручной деплой с Windows: git archive ломает sh-скрипты

- Источник: переезд стейджа 2026-11-12. `git archive HEAD` на машине
  владельца (core.autocrlf=true, без .gitattributes) конвертирует текстовые
  файлы в CRLF — на сервере `sh scripts/backup-prod.sh` падает
  с `set: Illegal option -`.
- В #188 (2026-11-15) добавлен `.gitattributes` для LF у shell-скриптов;
  далее правило распространено на Python, YAML и конфиги развёртывания.
  Для свежих checkout эти файлы сохраняют LF; старые рабочие копии могут
  требовать повторного checkout. Проверка:
  `git ls-files --eol scripts/*.sh` и Linux-прогон `scripts/test_deploy.py`.
- Обход: для ручной заливки использовать `git -c core.autocrlf=false
  archive HEAD | ssh ...`. Штатный путь — workflow Deploy на раннере
  Linux, там проблемы нет.

## FirstVDS Ubuntu 24.04: DNS в контейнерах и занятый порт 80

- Источник: первичная настройка 188.120.225.204, 2026-11-12.
- DNS: образ использует stub systemd-resolved (127.0.0.53), Docker копирует
  его в контейнеры, где stub недоступен — Let's Encrypt и любые внешние
  запросы из контейнеров падают с `read udp 127.0.0.53:53: connection
  refused`. Лечится `/etc/docker/daemon.json` с явным `dns`
  (указаны DNS FirstVDS 188.120.247.2/188.120.247.8) + restart docker.
- В образе предустановлен nginx, слушающий :80 — caddy не стартует
  (`address already in use`). Лечится `systemctl disable --now nginx`.
- При первичной настройке парольная аутентификация root была включена.
  **Обновлено 2026-11-16 по поручению владельца:** парольный и keyboard-interactive
  вход SSH отключены, root входит только по ключу. Конфигурация —
  `/etc/ssh/sshd_config.d/00-dkp-key-only.conf` (приоритет над
  `40-hosting.conf`); проверены `sshd -t`, `sshd -T`, новый вход по ключу
  и отказ без ключа (`Permission denied (publickey)`). Повторная проверка:
  `ssh -o BatchMode=yes -o PasswordAuthentication=no dkp-stage true`;
  эффективные параметры — `sshd -T` на сервере.

## Один GUILD_LEADER на базу: частичный unique-индекс

- Источник: спека `members/blocking.database.spec.ts` (#149), 2026-11-14.
  Симптом: `member.create({ rank: 'GUILD_LEADER' })` в тесте падает
  P2002-подобной ошибкой уникальности.
- Причина: в БД частичный unique-индекс разрешает ровно одного Главу
  (упоминается и в `auction-manage.database.spec.ts`). В dkp_test сид уже
  создаёт `ТестГлава`.
- Обход: в database-спеках не создавайте Главу — берите сидового через
  `member.findFirst({ where: { rank: 'GUILD_LEADER' } })`; права в сервисах
  читаются из актора, а не из строки члена.
- Повторная проверка: прогон спеки после переиспользования сидового Главы.

## Второй PrismaService в модуле грузит .env в process.env тестов

- Источник: PR #177, 2026-11-15, воспроизведено локально. Симптом:
  `discord.integration.spec.ts` («пустая конфигурация») стал ждать
  `{discord:false}`, а получал `discord:true` после добавления RealtimeModule
  в импорты AuthModule.
- Причина: RealtimeModule пере-предоставлял `PrismaService` — создавался
  второй PrismaClient, конструктор которого сам грузит `.env` в `process.env`
  (в т.ч. `DISCORD_*`), и изолированная спека с фейковой БД видела прод-env.
- Правило: модули НЕ пере-предоставляют PrismaService — он глобален из
  PrismaModule; для узких интерфейсов сервисов используйте фабрики с
  приведением типа (`prisma as unknown as SomeDb`).
- Повторная проверка: `pnpm -C apps/api exec jest src/auth/discord.integration.spec.ts`
  на чистом дереве — зелёный; после удаления дубля провайдера — зелёный
  и с RealtimeModule в импортах.

## Общая тестовая БД dkp_test: изоляция database-спек

- Источник: локальные прогоны 2026-11-10 при работе над #96. Симптом:
  тест «рестарт обработчика» в `auction-close.database.spec.ts` ожидал
  2 закрытия свипером, получал 3 — в базе оставались чужие просроченные
  OPEN-лоты.
- Причина: все `*.database.spec.ts` делят одну локальную `dkp_test`.
  Спека, оставившая после себя просроченный OPEN-лот (например,
  гонка-тест со ставкой, продлевающей окончание анти-снайпом на секунды),
  ломает счётчики свипера в чужих тестах при следующем прогоне. В CI
  база свежая, поэтому ловушка только локальная.
- Правило: убирать свои ряды в `afterAll` в FK-безопасном порядке
  (образец — `auction-manage.database.spec.ts`, префикс данных `mg-`);
  проверки «сколько всего закрыл свипер» не привязывать к строгому
  равенству — точность по своим id и статусам.
- Повторная проверка: два последовательных прогона
  `pnpm -C apps/api exec jest --runInBand --testPathPattern=database.spec.ts`
  с `ONBOARDING_TEST_DATABASE_URL` — 60/60 (2026-11-10).

## Git Bash: docker не на PATH

- Источник: #203, 2026-11-16, Windows-хост владельца. Симптом:
  `docker: command not found` в Git Bash при работающем Docker Desktop.
- Причина: каталог Docker не добавлен в PATH Git Bash; бинарники лежат
  в `/c/Program Files/Docker/Docker/resources/bin` (есть `docker.exe`).
- Обход: `export PATH="/c/Program Files/Docker/Docker/resources/bin:$PATH"`
  и вызывать `docker.exe compose up -d` (extensionless `docker` в том
  каталоге печатает usage). Повторная проверка: `docker version --format
  '{{.Server.Version}}'` возвращает версию движка.

## Локальный стенд dev-screenshot: watcher API переживал `down` (#296)

- Источник: #296, сессии #295 и #296, 2026-11-24; воспроизведено на Windows
  трижды, исправлено тем же issue (`scripts/dev-screenshot.sh`,
  `scripts/dev-screenshot-procs.ps1`).
- Как было: `down` снимал только слушателей портов. Порт API слушает
  дочерний процесс `nest start --watch`; watcher оставался живым и после
  реального изменения в `apps/api/src` возвращал API на `:3005` — следующий
  `up` падал «ПОРТ ЗАНЯТ». Одного `touch` для перезапуска недостаточно.
- Вторая причина, та же задача: пускающие субшеллы `( … nohup CMD >log & )`
  не подменяли себя командой, а ждали её с открытым stdout скрипта —
  конвейер `dev-screenshot.sh up | tail` не завершался, пока жив стенд,
  хотя сам скрипт уже напечатал «ГОТОВО» и вышел.
- Теперь: `up` запоминает пускачей в `.dev-screenshot.active`; `down` снимает
  их деревья и деревья слушателей портов этого каталога; прерванный `up`
  убирает за собой. Стенд другого каталога (вторая сессия в другом клоне)
  не трогается — `down` сообщает о нём и выходит с кодом 1, `up` не стартует.
- Ограничение: watcher без слушателя и без записи (остался от старой версии
  скрипта) `down` не найдёт. Его показывает `status` («пускач этого
  каталога»; там же обычный dev-API на :3001). Снять дерево вручную:
  `taskkill //PID <pid> //T //F`.
- Ловушки работы с процессами, проверенные там же:
  - у корня цепочки `ParentProcessId` ведёт к несуществующему процессу (так
    работает `exec` в MSYS) — дерево ищут от слушателя порта вверх, а не от
    скрипта вниз;
  - `taskkill /T /F` возвращает ошибку («операция не поддерживается»), если
    корень завершается сам после гибели потомков; результат сверяют по
    наличию процесса (`tasklist //FI "PID eq <pid>"`), а не по коду возврата;
  - PID в MSYS переживает `exec`: `/proc/<pid>/winpid` даёт текущий Windows
    PID процесса из любого шелла того же Git;
  - у фоновой команды неинтерактивного шелла SIGINT игнорируется с рождения —
    обработчик `INT` нельзя проверить через `kill -INT`, только `TERM`.
- Повторная проверка: `up` → `down` → добавить файл в `apps/api/src` →
  `netstat -ano | grep LISTENING | grep ':3005'` пусто; `… up | tail`
  возвращает управление сразу после «ГОТОВО».

## Discord OAuth с РФ-хостинга: блокировка по SNI, обход через zapret

- Источник: диагностика 2026-11-12 на FirstVDS 188.120.225.204. Симптом:
  вход через Discord падает с 500, в логах API `InternalOAuthError: Failed
  to obtain access token` / `ECONNRESET` к discord.com:443.
- Причина: ТСПУ режет TLS по SNI `discord.com` — TCP к IP Discord проходит,
  TLS с SNI cloudflare.com на тот же IP работает, с SNI discord.com — reset.
- Решение: zapret v72.13 на хосте (`/opt/zapret`, релиз с бинарниками,
  в git-клоне бинарников нет — качать asset релиза). Конфиг
  `/opt/zapret/config`: MODE_FILTER=hostlist, hostlist
  `ipset/zapret-hosts-user.txt` = домены Discord, стратегия
  `--filter-tcp=443 --dpi-desync=fake --dpi-desync-fooling=md5sig
  --dpi-desync-fake-tls=.../tls_clienthello_www_google_com.bin`
  (перебраны 7 стратегий, рабочая нашлась скриптом-прогоном; fake+ttl3,
  split2, multisplit не сработали). Правила в mangle/POSTROUTING покрывают
  и хост, и Docker-контейнеры (NAT). Сервис: `systemctl enable --now zapret`.
- Проверка: `curl -s https://discord.com/api/v10/gateway` с хоста и
  `docker exec dkp-guild-site-api-1 node -e "fetch(...)" ` → 200; callback
  с фейковым кодом даёт `invalid_grant` (Discord отвечает), а не сетевую
  ошибку. Если после смены провайдера/аплинка снова сломается — перебрать
  стратегии заново тем же прогоном.

## Кэш сборки Docker на VPS растёт с каждым деплоем

- Источник: проверка 24.11.2026 перед закрытием этапа 5, только чтение.
  Симптом: корневой раздел VPS занят на 85% (80 из 99 ГБ, свободно 15 ГБ).
- Причина: каждый Deploy (staging — после каждого слияния в `main`,
  production — по тегу) оставляет кэш BuildKit. `docker system df` показал
  Build Cache 76,42 ГБ, из них 75,07 ГБ очищаемо, активных записей 0; образы —
  2,9 ГБ, тома — 191 МБ. `du -x /var/lib/docker` кэш не видит — доверять
  `docker system df`. Когда диск заполнится, сломаются деплой и резервные
  копии.
- Безопасный обход: чистить только кэш сборки (`docker builder prune`, при
  необходимости `--keep-storage`), не во время Deploy и не удерживая общую
  блокировку `/run/lock/dkp-deploy.lock`; не применять `docker system prune`
  с `--volumes` и не трогать образы, тома и контейнеры. До и после записать
  `docker system df` и `df -h /`. Первый деплой после чистки идёт без кэша и
  дольше обычного. На 24.11.2026 кэш не очищался — владелец поручает это
  отдельной сессией.
- Повторная проверка: `docker system df` и `df -h /` на VPS. Чтобы кэш не рос
  снова, нужен шаг очистки в workflow деплоя или лимит сборщика в
  `daemon.json` — отдельным PR.
